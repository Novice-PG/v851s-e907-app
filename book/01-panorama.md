# 第 1 章 全景图：从一根串口到网页

> 本章目标：
> 1. 用一张图说清楚这个系统在干什么。
> 2. 知道 A7、E907、daemon、linkr-ble 各自的职责。
> 3. 学会用“三个问题”拆任何一层。

---

## 1.1 先回到问题本身

假设你有一块设备，它只有一个串口：

```text
目标设备
  ├─ TX  ── 它说话
  ├─ RX  ── 它听话
  └─ GND ── 共地
```

你想：

- 看它的启动日志。
- 给它敲命令。
- 把日志保存下来。
- 让同事在另一个房间也能看。
- 用手机临时连一下。

传统方案是：一台电脑 + USB 转串口 + 串口助手 + 人坐在旁边。

这个项目把“电脑 + 串口助手”换成了：

```text
一块 V851S 板子 + 浏览器/手机
```

板子自己联网，自己跑网页服务器，自己处理蓝牙。
目标设备仍然只看到一根普通串口，完全不知道 Wi-Fi 和 WebSocket 的存在。

> 这就是“透明桥”的思想：**不改变目标设备，只改变你接近它的方式。**

---

## 1.2 三层架构

先记住三层，不要一上来就钻代码：

```text
┌─────────────────────────────────────────────┐
│  表现层：浏览器网页 / 手机 App / TUI / CLI   │
│  负责：显示、输入、用户体验                   │
└───────────────────┬─────────────────────────┘
                    │ HTTPS / WebSocket / BLE
┌───────────────────▼─────────────────────────┐
│  服务层：linkr-bee-daemon / linkr-ble        │
│  负责：协议转换、会话、命令、认证、持久化      │
└───────────────────┬─────────────────────────┘
                    │ rpmsg（共享内存 + mailbox）
┌───────────────────▼─────────────────────────┐
│  硬件层：A7 Linux / E907 Zephyr / UART3      │
│  负责：启动、驱动、实时收发                   │
└───────────────────┬─────────────────────────┘
                    │ TX / RX / GND
                目标设备
```

### 每一层的一句话

| 层 | 一句话 | 典型问题 |
|---|---|---|
| 表现层 | 把字节画成终端，把键盘变成字节 | 页面打不开、按钮没反应 |
| 服务层 | 把网络协议翻译成串口字节 | 令牌错、连接断、命令不回 |
| 硬件层 | 把电平和寄存器变成字节流 | 乱码、丢包、E907 不启动 |

> 排障时先确定“问题在哪一层”，不要跨层猜。
> 页面打不开，不一定是串口坏了；串口乱码，也不一定是网页的错。

## 1.3 两个 CPU 的分工

V851S 里有两个处理器：

| CPU | 跑什么 | 负责 | 不负责 |
|---|---|---|---|
| Cortex-A7 | Linux 4.9 | 网络、网页、蓝牙、文件、SSH | 实时串口 |
| E907 | Zephyr 4.5 | UART3 收发、rpmsg | 网络、文件系统 |

为什么不让 A7 直接管 UART3？

1. **引脚归属**：这块板的 UART3 在 PE12/PE13，BSP 把它分配给 E907。
2. **实时性**：Linux 会被网络、Python、蓝牙抢占；串口 FIFO 不及时读会丢字节。
3. **隔离**：网页再忙，也不该把目标串口堵死；E907 的 64 KiB 缓冲能吸收突发。

> 这不是唯一正确的设计。换一块 A7 直接引出 UART 的板子，
> 完全可以让 Linux 直接管串口。书里讲的是“这块板 + 这个 BSP”的选择，
> 以及背后的通用方法。

## 1.4 三条链路

### 链路一：浏览器 ↔ daemon

```text
浏览器
  │  HTTPS（页面）
  │  WSS 或 WS（终端字节流）
  ▼
linkr-bee-daemon（Python）
```

- 页面来自 `/usr/share/linkr-bee/web`。
- 终端数据走 WebSocket：二进制帧是串口字节，文本帧是 `@...` 命令。
- 有令牌时，连接后 3 秒内要发令牌。

### 链路二：手机 ↔ linkr-ble

```text
手机
  │  BLE GATT
  ▼
BlueZ（bluetoothd）
  │  D-Bus
  ▼
linkr-ble（C/GLib）
  │  Unix socket
  ▼
linkr-bee-daemon
```

- BLE 不是“无线串口”，它是服务/特征值树。
- 手机往某个特征值写数据，BlueZ 通过 D-Bus 通知 linkr-ble。
- linkr-ble 把数据打包成帧，通过 Unix socket 交给 daemon。

### 链路三：daemon ↔ E907 ↔ 目标设备

```text
linkr-bee-daemon
  │  write(/dev/rpmsgN)
  ▼
Linux rpmsg_char
  │  共享内存 + vring + mailbox
  ▼
E907 Zephyr
  │  UART3
  ▼
目标设备
```

- daemon 不直接碰 UART3，它只写 rpmsg 端点。
- E907 把 rpmsg 数据放进 `uart_tx_ring`，再由 UART 线程发出去。
- 反方向：UART 中断把字节放进 `uart_rx_ring`，E907 再通过 rpmsg 推给 A7。

## 1.5 一次按键的完整旅程

你在网页终端里敲了一个 `l`：

```text
1. 浏览器键盘事件 -> WebSocket 二进制帧
2. daemon 收到帧，放进发送队列
3. daemon 按 256 字节切片，write(/dev/rpmsgN)
4. Linux rpmsg 把数据放进 vring，按 mailbox 门铃
5. E907 收到中断，取出数据，放进 uart_tx_ring
6. E907 的 UART 线程把 'l' 写到 UART3 TX
7. 目标设备收到 'l'
```

目标设备回了一个 `o`：

```text
1. UART3 RX 中断 -> E907 的 uart_rx_ring
2. E907 的 UART 线程取出 'o'，rpmsg_sendto()
3. Linux daemon 收到数据
4. daemon 广播给所有 WebSocket 客户端
5. 浏览器把 'o' 画在终端里
```

> 这条链路里，任何一层都可能失败。书后面的每一章，
> 都是把其中一层拆开。

## 1.6 为什么需要“协议”

如果只是转发字节，为什么还要 `@i?`、`@c claim`、`LINKRCFG`？

因为除了数据，你还需要：

- **诊断**：缓冲满没满？Wi-Fi 连没连？
- **控制**：改波特率、改广播名、申请控制权。
- **多客户端**：两个人同时打开网页，谁在敲键盘？
- **可靠性**：BLE 会丢包、会截断，需要序号和分片。

> 数据通道负责“字节”，控制通道负责“状态”。
> 两者分开，系统才能既传数据又管自己。

## 1.7 用“三个问题”拆任何一层

### 问题一：它在哪跑？

- 浏览器里：JavaScript。
- A7 用户态：Python daemon、C 的 linkr-ble。
- A7 内核：rpmsg_char、UART、USB、网络驱动。
- E907：Zephyr 线程、UART 驱动、OpenAMP。

### 问题二：它读写什么？

- 内存：环形缓冲、共享内存、vring。
- 寄存器：引脚复用、时钟、UART FIFO。
- 文件：`/dev/rpmsgN`、`/mnt/UDISK/...`、日志。
- socket：TCP 80/8443、Unix socket、BLE D-Bus。
- 网络：HTTP、WebSocket、Wi-Fi。

### 问题三：失败谁先发现？

- 硬件：E907 不启动、串口无输出。
- 驱动：`dmesg` 报错、设备节点不出现。
- daemon：日志、`@i?` 丢包计数、网页报错。
- 前端：控制台报错、连接状态变红。

> 这三个问题会贯穿全书。每读一段代码，都问一遍。

## 1.8 第一个实验：观察一个活着的系统

假设板子已经启动、联网。

### 实验 A：确认版本和 E907

```sh
cat /etc/rootfs_version
cat /sys/kernel/debug/remoteproc/remoteproc0/state
tail -5 /sys/kernel/debug/remoteproc/remoteproc0/trace0
```

预期：

```text
v851s-lizard-e907-v12-20261114
running (2)
e907 heartbeat ...
```

### 实验 B：确认服务

```sh
ps w | grep -E 'linkr-bee-daemon|bluetoothd|linkr-ble'
```

预期能看到三个进程（名称可能略有差异）。

### 实验 C：确认网页

```sh
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1/
curl -sk -o /dev/null -w '%{http_code}\n' https://127.0.0.1:8443/
```

预期：

```text
301
200
```

### 实验 D：确认串口设备

```sh
ls -l /dev/rpmsg* /dev/ttyS2
```

预期能看到 `/dev/rpmsg_ctrl0`、一个或多个 `/dev/rpmsgN`、
以及蓝牙用的 `/dev/ttyS2`。

> 如果这些实验失败，先别往下读。回到第 0 章的“分层定位”，
> 从电源和串口开始查。
