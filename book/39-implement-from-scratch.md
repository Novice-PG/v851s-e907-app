# 第 39 章 从零做一遍：分阶段实施

> 本章目标：
> 1. 会把一个大项目切成“每步都能验证”的阶段。
> 2. 知道每个阶段的输入、输出、验收和常见卡点。
> 3. 理解“先打通、再加固、最后优化”的顺序为什么不能反。
> 4. 能用最小代价验证最危险的假设。
> 5. 有一份可以照着做的实施清单。

---

## 39.1 阶段划分

```text
P0  环境与工具链
P1  板子能启动、能登录
P2  E907 能跑 hello
P3  A7 ↔ E907 能通信（rpmsg）
P4  E907 能收发 UART3
P5  A7 能把字节转给浏览器（WS）
P6  会话与命令（owner、@ 命令）
P7  HTTPS 与令牌
P8  BLE
P9  多端统一与前端适配
P10 工程化：镜像、刷机、测试、性能
P11 安全与交付
```

### 为什么是这个顺序

```text
每一阶段只引入一个新的不确定性。
上一个阶段没验证，绝不进入下一个。
```

反例：

```text
一上来就写 BLE + HTTPS + 前端
→ 出问题时不知道是哪一层
→ 每一层都要单独调试，成本翻倍
```

> 排阶段的本质是：**把“同时怀疑五件事”变成“一次只怀疑一件事”。**

## 39.2 P0：环境与工具链

### 目标

```text
能在主机上编译出目标板可执行的程序
```

### 需要

```text
- Linux 主机（Ubuntu 22.04 或类似）
- 交叉工具链（arm-none-linux-gnueabi / aarch64 视板而定）
- Zephyr SDK（RISC-V）
- CMake、Ninja、Python 3
- 串口工具（picocom/minicom）
- 网络工具（ssh、scp、curl）
```

### 验收

```sh
# 交叉编译一个 hello
arm-linux-gnueabi-gcc -o hello hello.c
file hello
# ELF 32-bit LSB executable, ARM

# Zephyr 环境
echo $ZEPHYR_BASE
west --version
```

### 常见卡点

| 现象 | 原因 |
|---|---|
| 找不到工具链 | PATH 没设 |
| `west` 报错 | 没在 workspace 里 |
| 编译出的程序跑不了 | 架构/ABI 不匹配 |
| 串口没权限 | 没加 `dialout` 组 |

> P0 不通过，后面全是空谈。**先把工具链跑通。**

## 39.3 P1：板子能启动、能登录

### 目标

```text
串口看到启动日志，能登录 shell，能联网
```

### 步骤

```text
1. 接串口（GND、TX、RX），115200 8N1
2. 上电，看 U-Boot 和内核日志
3. 登录（串口或 SSH）
4. 配 Wi-Fi，拿到 IP
5. 确认时间正确（TLS 需要）
```

### 验收

```sh
cat /proc/cpuinfo
uname -a
ip addr show wlan0
date
ping -c1 192.168.0.1
```

### 常见卡点

| 现象 | 原因 |
|---|---|
| 串口全是乱码 | 波特率/地线/电平 |
| 没有输出 | 串口接反、供电不足 |
| 能登录但没网 | 凭据、regulatory domain |
| TLS 报证书过期 | 系统时间错 |

> **时间不对会让 HTTPS 失败**，而且报错很难懂。先 `date` 一下。

## 39.4 P2：E907 能跑 hello

### 目标

```text
E907 固件能被 Linux 加载，能输出一行字
```

### 为什么难

```text
- 没有独立调试器时，只能靠 RAM console
- 固件格式（ELF + resource table）必须对
- 内存地址必须和 DTS 一致
```

### 最小固件

```c
#include <zephyr/kernel.h>

int main(void)
{
    printk("e907 hello\n");
    for (;;) {
        k_sleep(K_SECONDS(1));
    }
}
```

### 加载

```sh
echo stop  > /sys/class/remoteproc/remoteproc0/state
echo start > /sys/class/remoteproc/remoteproc0/state
cat /sys/class/remoteproc/remoteproc0/state     # running
```

### 验收

```text
- state = running
- RAM console 里出现 "e907 hello"
- dmesg 没有 remoteproc 错误
```

### 常见卡点

| 现象 | 原因 |
|---|---|
| state 一直 offline | 固件路径/格式错 |
| 加载后立刻崩 | 内存地址/DTS 不匹配 |
| 没有任何输出 | RAM console 没配、地址错 |
| `resource_table` 缺失 | 链接脚本/配置 |

> P2 是整本书最“硬件”的一步。**它过了，后面都是软件。**

## 39.5 P3：A7 ↔ E907 能通信

### 目标

```text
A7 发一条消息，E907 收到并回复
```

### 最小 rpmsg

```c
/* E907 侧 */
static void rpmsg_cb(const struct device *dev, void *data, size_t len,
                     uint32_t src, void *priv)
{
    printk("rx %zu bytes from %u\n", len, src);
    /* 回显 */
}
```

```python
# A7 侧
fd = os.open("/dev/rpmsg0", os.O_RDWR)
os.write(fd, b"ping")
print(os.read(fd, 64))
```

### 验收

```text
- /dev/rpmsgN 存在
- 发 "ping" 收到 "pong"
- 连续发 1000 条不丢
```

### 常见卡点

| 现象 | 原因 |
|---|---|
| 没有 `/dev/rpmsg*` | vring/resource table 不对 |
| 打开失败 | 权限、endpoint 没创建 |
| 发出去没回 | E907 回调没注册 |
| 大量丢 | 缓冲太小、没背压 |

> 这是“异构”的核心。**先跑通一条消息，再谈吞吐。**

## 39.6 P4：E907 能收发 UART3

### 目标

```text
目标板发什么，E907 收到什么；E907 发什么，目标板收到什么
```

### 步骤

```text
1. 确认 UART3 的地址、时钟、引脚复用
2. 配 115200 8N1
3. 中断收，环形缓冲
4. 发送走 FIFO + 中断
```

### 验收

```sh
# 目标板侧
echo "hello from target"

# 主机串口（/dev/ttyUSB0）
hello from target
```

```sh
# 反向
printf 'ping\r\n' > /dev/ttyUSB0
# E907 的 RAM console 里看到 "ping"
```

### 常见卡点

| 现象 | 原因 |
|---|---|
| 全是乱码 | 时钟/波特率算错 |
| 收不到 | 引脚复用没配、RX 没使能 |
| 发不出 | TX 引脚、FIFO 没推 |
| 偶尔丢字节 | 中断优先级、缓冲太小 |

> UART 是“看起来最简单、实际最容易错”的外设。**时钟一定要自己算一遍。**

## 39.7 P5：A7 能把字节转给浏览器

### 目标

```text
浏览器打开页面，看到串口输出，能输入字符
```

### 最小实现

```text
1. HTTP 服务（静态页面）
2. WebSocket 握手
3. 二进制帧 ↔ rpmsg
4. 页面用 xterm.js 显示
```

### 验收

```text
- 打开 http://<board>/ 看到终端
- 输入 "ls" 回车，目标板执行
- 目标板输出出现在页面
```

### 常见卡点

| 现象 | 原因 |
|---|---|
| 页面打不开 | 端口/防火墙/服务没起 |
| WS 握手失败 | `Sec-WebSocket-Accept` 算错 |
| 能连但不显示 | 帧解析错（掩码/长度） |
| 输入没反应 | 前端没发、后端没转发 |

> 到这一步，你已经有一个“能演示”的系统了。

## 39.8 P6：会话与命令

### 目标

```text
多客户端、owner、@ 命令、事件
```

### 要加

```text
- Session（客户端表、owner、epoch）
- handle_text / handle_binary
- @i? @u? @w? @s? @c?
- 事件路由（final/error）
```

### 验收

```text
- 两个浏览器同时连，只有一个能写
- @c? 返回正确 owner
- @c release 后不自动 reclaim
- @i? 返回完整诊断
```

### 常见卡点

| 现象 | 原因 |
|---|---|
| 两个终端互相插字 | 没有 owner |
| owner 不释放 | unregister 没清 |
| 命令回复进了串口 | 没剥离 `LINKR*` |
| 事件重复 | reqid 匹配错 |

> 这一步把“能演示”变成“能多人用”。

## 39.9 P7：HTTPS 与令牌

### 目标

```text
8443 可用，80 跳转，令牌生效
```

### 步骤

```text
1. 生成自签名证书（含 SAN）
2. Python 的 ssl 包一层
3. 80 端口只做 301
4. 第一帧要求令牌
```

### 验收

```sh
curl -sI http://<board>/ | head -1        # 301
curl -sk https://<board>:8443/ | head -1  # 200
```

```text
错误令牌 → 被拒
正确令牌 → 可用
```

### 常见卡点

| 现象 | 原因 |
|---|---|
| 浏览器一直警告 | 自签名（正常） |
| `SSL_ERROR` | 证书/私钥不匹配 |
| 时间错导致失败 | 系统时间 |
| 令牌不生效 | 第一帧顺序错 |

## 39.10 P8：BLE

### 目标

```text
手机能扫到、连上、收发
```

### 步骤

```text
1. hci0 up
2. 注册 GATT 服务（NUS / Management / Reliable）
3. 广播
4. 手机连上、订阅、收发
```

### 验收

```text
hciconfig hci0          # UP RUNNING
ps | grep linkr-ble
# 手机上能看到设备，订阅后收到数据
```

### 常见卡点

| 现象 | 原因 |
|---|---|
| 扫不到 | 广播数据没写（第 22 章的内核 bug） |
| 连不上 | 已有 central、配对失败 |
| 能写收不到 | CCCD 值错（notify vs indicate） |
| 数据截断 | MTU 没协商 |

> P8 是最容易被“环境问题”卡住的一步。**先把广播跑通。**

## 39.15 时间与风险

### 一个现实的分布

```text
P0-P1   10%   环境问题最耗时
P2-P3   30%   异构通信最难
P4      10%   UART 细节多
P5-P6   20%   协议与并发
P7-P8   15%   证书与 BLE
P9-P11  15%   工程化收尾
```

### 最容易低估的

```text
1. 环境（工具链、串口、网络）
2. BLE（厂商栈、权限、配对）
3. 刷机（救援流程、回滚）
4. 长稳（要等）
```

> 排期时给这四项各留一倍缓冲。

### 风险登记

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| E907 固件加载失败 | 中 | 高 | 先跑 hello |
| BLE 广播为空 | 高 | 中 | 绕过脚本 |
| 刷机变砖 | 低 | 高 | 救援流程 + 备份 |
| 内存不足 | 中 | 中 | 早做基线 |

## 39.17 常见错误清单

| 现象 | 可能原因 | 怎么查 |
|---|---|---|
| 一直集成不了 | 没做垂直切片 | 先打通一条 |
| 同时怀疑多层 | 阶段没隔离 | 回上一个验证点 |
| 环境问题耗一周 | 没先做 P0 | 补工具链检查 |
| E907 一直 offline | 固件/地址 | 先跑 hello |
| 刷机后起不来 | 动了启动链 | 用救援 + 备份 |
| 长稳才发现泄漏 | 没早做基线 | 每阶段记录内存 |
| 安全最后补 | 架构没留位置 | 认证尽早加 |
| 文档最后写 | 细节已忘 | 每阶段写一段 |
