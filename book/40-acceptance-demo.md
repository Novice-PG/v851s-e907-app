# 第 40 章 验收与交付：把“我做完了”变成证据

> 本章目标：
> 1. 会把需求逐条映射到可执行的验收步骤。
> 2. 会做一份 10 分钟的演示，且每条都对应一个需求。
> 3. 知道交付包含什么：镜像、文档、凭据、回滚、支持边界。
> 4. 会处理演示现场故障，不靠运气。
> 5. 能写一份让下一个人接得住的交接文档。

---

## 40.1 什么叫“做完了”

三种常见回答：

```text
“能跑了”           → 只证明 happy path
“我测过了”         → 没有记录，无法复现
“这是验收记录”     → 有版本、有步骤、有结果
```

第三种才是交付。

### 验收的三个层次

```text
1. 功能：每条需求都能演示
2. 质量：长稳、性能、安全达标
3. 可交付：别人能重建、能刷机、能回滚
```

> 只做到 1，是 demo；做到 3，才是产品。

## 40.2 需求 → 验收矩阵

### 示例

| 编号 | 需求 | 验收步骤 | 期望 | 结果 |
|---|---|---|---|---|
| F1 | 网页看串口 | 打开 `https://<board>:8443/`，目标板发 `hello` | 页面显示 | ✅ |
| F2 | 网页发字符 | 输入 `uname -a` 回车 | 目标板返回 | ✅ |
| F3 | BLE 连接 | 手机扫描并订阅 | 收到数据 | ✅ |
| F4 | 诊断 | `@i?` | `@info ... @info done` | ✅ |
| F5 | 改波特率 | `@u=9600,8,n,1,n` | `OK`，双方生效 | ✅ |
| F6 | 令牌 | 错令牌被拒，对令牌通过 | 4 / 0 | ✅ |
| N1 | 延迟 < 50 ms | 100 次时间戳取 P95 | < 50 ms | ✅ |
| N2 | 24h 内存 < +10% | soak 曲线 | +4% | ✅ |
| N3 | 2 WS + 1 BLE | 同时连接 | 无丢包 | ✅ |
| N4 | 断线 5s 重连 | 拔网线再插 | 自动恢复 | ✅ |
| N5 | 掉电不丢配置 | 断电 5 次 | 令牌/证书在 | ✅ |
| N6 | 镜像无凭据 | `unsquashfs -l \| grep key` | 无输出 | ✅ |

### 写法要求

```text
1. 一条需求一行
2. 步骤要具体到命令/点击
3. 期望要可判定（数字/字符串/状态）
4. 结果列留空，现场填
```

> 验收矩阵不是“写给别人看的”，是**你自己照着做的清单**。

## 40.3 演示脚本

### 10 分钟结构

```text
0:00  一句话：这是什么，解决什么问题
0:30  架构图：三条链路
1:30  演示 1：网页 ↔ 串口
3:00  演示 2：多客户端 owner
4:00  演示 3：BLE
5:30  演示 4：诊断与配置
6:30  演示 5：断线重连 / 重启恢复
8:00  数据：延迟、内存、长稳
9:00  边界：已知限制、不做的事
9:30  下一步 / 提问
```

### 每条演示都要对应需求

```text
演示 1 → F1、F2、N1
演示 2 → F4、owner（第 31 章）
演示 3 → F3
演示 4 → F4、F5、F6
演示 5 → N4、N5
数据   → N2、N3
```

> 演示不是“展示功能”，是**证明需求**。

### 演示前检查

```sh
# 板子
cat /etc/rootfs_version
cat /sys/class/remoteproc/remoteproc0/state
ss -ltn | grep -E ':80|:8443'
pgrep -f linkr-bee-daemon
pgrep -f linkr-ble

# 目标板
# 串口能通

# 手机
# 蓝牙开、App 已安装、已配对

# 网络
ping -c1 <board>
```

### 演示的“脏”准备

```text
- 提前登录好，不要现场输密码
- 提前打开页面，不要现场找 URL
- 准备一份录屏，网络挂了能放
- 准备一份日志/截图，作为“刚才跑过”的证据
```

> 现场最怕的不是失败，是**失败后没有退路**。

## 40.4 现场故障处理

### 原则

```text
1. 不要现场 debug
2. 先切到备份路径（录屏/截图/另一块板）
3. 记录现象，演示后再说
```

### 常见故障与台词

| 故障 | 处理 |
|---|---|
| 板子没起来 | 切录屏：“这是今早的完整流程” |
| 网页打不开 | 用 CLI 演示同一命令 |
| BLE 连不上 | 用另一台手机/录屏 |
| 网络断了 | 切本地串口演示 |
| 投影不显示 | 提前准备 PDF |

### 不要说的话

```text
“奇怪，刚才还好好的”      → 暴露没有准备
“你等我一下”              → 让所有人等你 debug
“这个不重要”              → 观众会认为都不重要
```

### 应该说

```text
“这一步在我的验收记录里是第 7 项，结果在这里。”
“现场环境有个差异，我切到录屏，之后会补一份说明。”
```

> 诚实 + 有证据，比“强行成功”更可信。

## 40.5 交付物清单

### 必须有

```text
1. 镜像 + SHA256SUMS + 发布说明
2. 源码仓库（含 LICENSE / NOTICE / MANIFEST）
3. 文档：README / BUILD / DEPLOY / PROTOCOL
4. 验收记录（本矩阵 + 长稳数据）
5. 回滚方案
6. 凭据清单（说明在哪、怎么换，不含明文）
7. 支持边界（什么管、什么不管）
```

### 镜像

```text
rootfs.squashfs
boot-normal.img
boot-rescue.img
v851s_linux_lizard_uart0.img
SHA256SUMS
README.md（版本、改动、刷机、验收）
```

### 源码

```text
git tag（对应镜像版本）
MANIFEST.sha256
构建脚本
```

### 文档

```text
README        这是什么
BUILD         怎么构建
DEPLOY        怎么部署
PROTOCOL      协议
EXPLAIN       为什么这么设计
```

### 验收记录

```text
日期、版本、执行人
矩阵逐项结果
长稳曲线/数据
已知问题
```

> 交付物的判据：**别人只拿这些，能不能自己跑起来并判断好坏？**

## 40.6 支持边界

### 必须写清楚

```text
支持：
- 这块板 + 这个镜像
- 按文档的部署方式
- 已列出的功能

不支持：
- 改硬件
- 第三方固件
- 未列出的使用方式
- BLE 双连接（控制器限制）
```

### 为什么重要

```text
没有边界 → 所有问题都是你的问题
有边界   → 超出范围的需求可以被讨论，而不是默默背锅
```

### 已知限制要具体

```text
好：BLE 同时只支持 1 个 central（XR829 固件限制，软件无法绕过）
坏：BLE 有些不稳定
```

> 限制写得越具体，越显得可信。

## 40.7 交接文档

### 结构

```markdown
# 交接：<项目> <版本>

## 1. 现在是什么状态
一句话 + 版本号 + 能做什么。

## 2. 从哪开始
三条命令：构建、部署、验证。

## 3. 关键设计
5 条以内，每条一句 + 指向 ADR/章节。

## 4. 已知问题
按严重程度排序，每条写“影响 + 绕过方法”。

## 5. 常见操作
重启服务、换固件、刷机、回滚。

## 6. 凭据在哪
路径 + 权限 + 轮换方法（不含明文）。

## 7. 谁负责什么
硬件/固件/上层/文档。

## 8. 下一步建议
按优先级。
```

### 关键：可执行

```text
“重启服务”要写成：
  ssh root@<board> '/etc/init.d/S53linkr restart'
```

> 交接文档的读者是**半年后的陌生人**（可能是你自己）。

## 40.9 实验

### 实验 A：做验收矩阵

把你的需求逐条写成“步骤 + 期望 + 结果”，至少 12 行。

### 实验 B：跑一遍

按矩阵实际执行，记录每项耗时和结果。失败的项写“原因 + 下一步”。

### 实验 C：写演示脚本

按 40.3 的结构写 10 分钟脚本，标出每条对应哪个需求。

### 实验 D：故障演练

故意制造三个故障（拔网线、停服务、关蓝牙），练习切换备份路径。

### 实验 E：写交接文档

按 40.7 的结构写一份，然后让没参与的人读，记录他问了什么。

## 40.10 常见错误清单

| 现象 | 可能原因 | 怎么查 |
|---|---|---|
| 验收时说不清 | 没有矩阵 | 补需求映射 |
| 演示超时 | 没排练 | 计时跑三遍 |
| 现场翻车 | 没备份路径 | 录屏 + CLI |
| 交付后一直有人问 | 文档缺口 | 补 FAQ/交接 |
| “能用”但不可复现 | 没版本/校验和 | 发布流程 |
| 需求漏了 | 矩阵没覆盖 | 逐条对照 |
| 限制说不清 | 没写已知问题 | 列清单 |
| 回滚没演练 | 只写在文档 | 真跑一次 |

## 40.13 写在最后

这本书从“会一点 C 和几条 Linux 命令”开始，到这里你已经走完：

```text
看懂原理图与地址
→ 理解启动链与存储
→ 让第二颗核跑起来
→ 打通 rpmsg 与 UART
→ 写 daemon、WebSocket、HTTPS
→ 接 BLE 与手机
→ 统一四种端的协议
→ 构建、刷机、测试、优化
→ 安全、文档、许可证
→ 需求、实施、验收
```

真正重要的不是记住每个寄存器，而是这几件事：

```text
1. 遇到问题先分层，一次只怀疑一件事
2. 每个结论都要有测量或日志
3. 每个改动都要能回滚
4. 每个交付都要有记录
5. 把“为什么”写下来
```

> 设备会过时，芯片会停产，但这些方法不会。
> 下一块板、下一颗核、下一种协议，你都能用同样的方式拆开。

祝你做得出来，也交付得出去。
