# 第 24 章 吞吐、分片与可靠性

> 本章目标：
> 1. 会估算 UART、rpmsg、BLE、WebSocket 四段的吞吐上限。
> 2. 知道 BLE 吞吐受哪些参数影响，怎么调。
> 3. 理解分片、节流、窗口、确认的取舍。
> 4. 会设计一个“可测、可复现”的吞吐实验。
> 5. 能判断瓶颈在哪一段，而不是盲目调参数。

## 24.1 先算清楚：四段串联

```text
目标板 UART3
  │  115200 / 1.5M / 4M
E907（环 + rpmsg）
  │  256 B/消息
A7 daemon（rpmsg + 队列）
  │
  ├─ WebSocket（LAN）
  └─ BLE（手机）
```

总吞吐 = **最慢那一段**。

### 各段上限（数量级）

| 段 | 上限 | 受什么限制 |
|---|---|---|
| UART 115200 | ~11.5 KB/s | 波特率 |
| UART 1.5M | ~150 KB/s | 波特率 |
| rpmsg | 几 MB/s | 共享内存 + 中断 |
| WebSocket | 几十 MB/s | CPU/网络 |
| BLE（MTU 247） | 50～200 KB/s | 连接间隔、MTU |
| BLE（MTU 23） | 5～20 KB/s | 每包 20 字节 |

**结论：默认 115200 时，UART 就是瓶颈；BLE 只有在高波特率
下才成为瓶颈。**

> 调优前先确认瓶颈。把 BLE 调到 200 KB/s，但 UART 只有
> 11 KB/s，等于白费。

## 24.2 UART 吞吐

### 公式

```text
字节/秒 = 波特率 / 每字节位数
每字节位数 = 1 起始 + 数据位 + 校验位 + 停止位
```

115200 8N1：

```text
10 位/字节
115200 / 10 = 11520 字节/秒 ≈ 11.5 KB/s
```

1.5 Mbaud：

```text
1500000 / 10 = 150000 字节/秒 ≈ 146 KB/s
```

### 怎么提高

1. 提高波特率（两端一致）。
2. 减少数据位/校验/停止位（8N1 已是最小常用）。
3. 开硬件流控（RTS/CTS），但需要额外引脚。
4. 压缩数据（协议层）。

### 环大小与突发

E907 64 KiB 环：

```text
115200:  65536 / 11520 ≈ 5.7 秒
1.5M:    65536 / 150000 ≈ 437 ms
4M:      65536 / 400000 ≈ 164 ms
```

> 环只能吸收**突发**，不能提高**持续**吞吐。

## 24.3 rpmsg 吞吐

### 每消息开销

```text
512 B buffer
- 16 B rpmsg 头
= 496 B payload
```

daemon 每次只发 256 B，是保守值。

### 消息速率

rpmsg 的瓶颈通常是：

- mailbox 中断频率。
- 每次通知的处理时间。
- vring 大小（8 个 buffer）。

如果每条消息都触发一次中断：

```text
256 B/消息 × N 消息/秒
```

中断处理假设 10 µs：

```text
100,000 次/秒 × 256 B = 25.6 MB/s   （理论上限）
```

实际远低于此，因为 A7 用户态 `read/write` 有系统调用开销。

> 对这块板，rpmsg 不是瓶颈。UART 和 BLE 才是。

## 24.4 BLE 吞吐：参数决定一切

### 关键参数

| 参数 | 影响 |
|---|---|
| MTU | 每包 payload |
| 连接间隔（Connection Interval） | 多久传一次 |
| 每间隔包数（Packets per Interval） | 一次传几个 |
| PHY | 1M / 2M |
| notify vs indicate | 有无确认 |
| 应用层节流 | 主动限速 |

### 简化公式

```text
吞吐 ≈ (MTU - 3) × 每间隔包数 / 连接间隔
```

例子：

```text
MTU 247, 4 包/间隔, 间隔 15 ms
(247-3) × 4 / 0.015 ≈ 65 KB/s
```

MTU 23：

```text
(23-3) × 4 / 0.015 ≈ 5.3 KB/s
```

### 这块板的实际策略

```c
nus_next_us = now + 5000;          /* 每 5 ms 一轮 */
for (i = 0; i < 4; i++) { ... }    /* 一轮最多 4 包 */
```

→ 每 5 ms 最多 4 × att_chunk。

MTU 247：

```text
4 × 244 / 0.005 = 195 KB/s 理论
```

实际受连接间隔限制，通常 30～80 KB/s。

### 为什么不能无限快

- 控制器 TX 缓冲有限。
- 手机处理通知有开销。
- 蓝牙协议栈有流控。
- 发太快会丢或触发断开。

> 节流是**必须**的，不是保守。没有节流，吞吐反而更低
> （因为丢包 + 重传）。

## 24.5 分片：每一层都要切

### 四层分片

```text
应用层：一条命令可能几 KB
  │
  ├─ rpmsg：256 B/消息
  │
  ├─ BLE ATT：att_chunk（20..514）
  │
  └─ BLE 链路层：27 B/包（1M PHY）
```

每层都有自己的上限，必须逐层切。

### rpmsg 切片

```python
while sent < len(view):
    chunk = view[sent:sent + self.max_chunk]
    n = os.write(self.fd, chunk)
    sent += n
```

### BLE 切片（NUS）

```c
gsize n = MIN(att_chunk, serial_in->len);
emit_value(NUS_TX, serial_in->data, n);
g_byte_array_remove_range(serial_in, 0, n);
```

### BLE 切片（Management）

Management 有自己的 12 字节头 + 长度字段，接收方按长度
累积分片。这是**应用层分片**，比依赖 ATT 的“长写”更可控。

### 为什么不用 ATT 的 Long Write

ATT 有 `Prepare Write` / `Execute Write` 机制，但：

- 依赖 MTU 和控制器实现。
- BlueZ 的 D-Bus 接口不直接暴露。
- 出错时难调试。

应用层自己分片，逻辑清晰、可测。

## 24.6 可靠性：三种机制

### 机制一：链路层重传

BLE 链路层对每个包有 ACK/重传。这是**底层可靠**。

- 对用户透明。
- 延迟增加。
- 不能保证“应用层顺序”。

### 机制二：indicate 确认

indicate 要求客户端回 ATT confirmation。

- 发送方知道“对方收到了”。
- 吞吐降低（一次一个）。
- 适合关键状态。

### 机制三：应用层序号

Reliable UART 服务：

```text
帧头带 seq
接收方按 seq 顺序接受
重复丢弃
乱序报 gap
```

这是**顺序保证**，不是重传。

### 三种机制怎么配合

```text
链路层：保证单包尽量到达
indicate：保证应用层帧被确认
seq：保证顺序和去重
```

> 真正的“端到端可靠”还需要应用层 ACK/NACK + 重传。
> 这块板选择了“BLE 链路可靠 + seq 顺序”，够用且简单。

### 什么时候需要更强

- 传文件/固件（不能错一个字节）。
- 跨公网（丢包率高）。
- 需要断点续传。

那时应该用：

- 分块 + 校验（CRC/hash）。
- 确认 + 重传。
- 窗口/流量控制。

## 24.7 怎么测吞吐

### 原则

1. **固定变量**：一次只改一个参数。
2. **测足够长**：至少 10 秒，避免启动抖动。
3. **记录两端**：发送方和接收方都计数。
4. **看丢包**：吞吐高但丢一半，等于没用。

### UART 测法

用目标板发已知模式：

```sh
# 目标板（Linux）
yes "0123456789abcdef" | head -c 1000000 > /tmp/data
cat /tmp/data > /dev/ttyS0
```

A7 侧统计 `LINKRSTAT` 和实际收到字节数。

### BLE 测法

手机 App 或脚本订阅 NUS TX，统计每秒字节数。

### WebSocket 测法

```python
import time, websocket
ws = websocket.create_connection("ws://<board>/ws")
ws.send(token)  # 如果有
start = time.time()
n = 0
while time.time() - start < 10:
    data = ws.recv()
    n += len(data)
print("bytes/s", n / 10)
```

### 记录模板

| 测试 | 波特率 | MTU | 间隔 | 发送 | 接收 | 丢 | 吞吐 |
|---|---|---|---|---|---|---|---|
| A | 115200 | 247 | 15 ms | 1 MB | 1 MB | 0 | 11.4 KB/s |
| B | 1.5M | 247 | 15 ms | 10 MB | 9.8 MB | 2% | 120 KB/s |
| C | 1.5M | 23 | 15 ms | 10 MB | 4 MB | 60% | 4 KB/s |

> 没有表格的“感觉快了”不是数据。

## 24.8 调优顺序

### 第一步：确认 UART 参数

```text
@u?
LINKRCFG OK uart=115200,8,n,1,n
```

如果目标板支持，提到 1.5M：

```text
@u=1500000,8,n,1,n
```

### 第二步：确认 MTU

```sh
cat /var/run/linkr-bt-mtu/*
```

如果只有 23，说明手机/协商有问题。

### 第三步：看丢包

```text
LINKRSTAT rx=... tx=... drop=...
```

- `drop_rx`：E907 环满。
- `drop_tx`：A7 发太快。

### 第四步：调节流

如果丢包严重，降低发送频率：

```c
nus_next_us = now + 10000;   /* 10 ms 而不是 5 ms */
```

### 第五步：换服务

小 MTU 设备用 NUS；大 MTU 且要顺序用 Reliable。

### 实验 A：UART 回环吞吐

把目标板 TX/RX 短接，发 1 MB，测往返。得到 UART 层上限。

### 实验 B：rpmsg 吞吐

不接 UART，用 `rpmsg_bench` 工具测 A7↔E907 往返。

### 实验 C：WebSocket 吞吐

用 24.7 的脚本，单独测 LAN。

### 实验 D：BLE 吞吐

用手机工具订阅，统计通知字节数。

### 对比

```text
UART 层     11.5 KB/s
rpmsg       > 1 MB/s
WebSocket   > 10 MB/s
BLE         30～80 KB/s
```

→ 瓶颈在 UART（默认）或 BLE（高波特率）。

## 24.10 常见错误清单

| 现象 | 可能原因 | 怎么查 |
|---|---|---|
| 吞吐上不去 | UART 波特率低 | `@u?` |
| BLE 只有几 KB/s | MTU 23 | MTU 目录 |
| 吞吐高但丢包 | 节流太激进 | `LINKRSTAT` |
| 大文件传一半断 | 窗口/缓冲满 | 日志、drop |
| 延迟忽大忽小 | 连接间隔/重传 | 抓包 |
| 控制命令慢 | 数据占满队列 | 背压/优先级 |
| 测出来不稳定 | 测试太短/环境干扰 | 延长、固定环境 |
| 改参数没效果 | 改错层 | 先定位瓶颈 |
| 丢字节但计数为 0 | UART FIFO overrun | 降速、查 ISR |
| 手机端卡顿 | 通知太密 | 降频 |
