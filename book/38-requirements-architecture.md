# 第 38 章 需求与架构：先想清楚，再动手

> 本章目标：
> 1. 会把“我想要一个……”变成可验证的需求。
> 2. 会画上下文图、分层图、时序图，并知道每张图回答什么问题。
> 3. 能做关键取舍：单核还是双核、轮询还是中断、Python 还是 C。
> 4. 会写架构决策记录（ADR），把“为什么”留下来。
> 5. 能识别“需求没想清楚”的典型症状。

## 38.1 从一句话到一份需求

### 起点

```text
“我想做一个能把串口搬到网页上的小板子。”
```

这句话信息量很少：

```text
- 给谁用？
- 同时几个人用？
- 要多快？
- 断网怎么办？
- 要不要手机？
- 数据要不要留？
```

### 拆成四类

```text
功能需求（做什么）
非功能需求（多快、多稳、多安全）
约束（不能改的）
验收标准（怎么算做完）
```

### 功能需求

用“角色 + 动作 + 结果”写：

```text
F1  用户可以打开网页，看到目标板的串口输出
F2  用户可以输入字符，发送到目标板
F3  用户可以通过手机 BLE 连接
F4  用户可以查看固件版本、缓冲区状态
F5  用户可以修改波特率
F6  用户可以设置访问令牌
```

### 非功能需求

必须带数字：

```text
N1  串口 115200 8N1 下，端到端延迟 < 50 ms（局域网）
N2  连续运行 24 小时，内存增长 < 10%
N3  支持 2 个网页 + 1 个 BLE 同时连接
N4  断线后 5 秒内自动重连
N5  掉电后配置不丢
N6  镜像不含任何凭据
```

> **没有数字的需求不是需求，是愿望。**

### 约束

```text
C1  DDR 只有 64 MB
C2  NAND 只有 128 MB
C3  必须保留 final7 启动链
C4  E907 只有 4 MB DRAM
C5  不能改厂商 XR829 固件
C6  遵守 Allwinner EULA，不分发 SDK
```

约束是**边界**，不是可选项。设计必须在约束内成立。

### 验收标准

每条需求都要有“怎么测”：

| 需求 | 验收 |
|---|---|
| F1 | 浏览器打开，看到 `# ` 提示符 |
| N1 | 打时间戳，测 100 次取 P95 |
| N2 | 24h soak，看 VmRSS 曲线 |
| N3 | 3 个客户端同时发，无丢包 |
| N6 | `unsquashfs -l \| grep key` 无输出 |

> 写不出验收标准的需求，通常也写不出实现。

## 38.2 上下文图：谁和谁说话

```text
                 ┌──────────────┐
   用户浏览器 ───►│              │
                 │              │──► 目标板（UART3）
   手机 App  ────►│   设备       │
                 │              │──► 局域网（Wi-Fi）
   SSH 用户  ────►│              │
                 └──────────────┘
                        │
                        ▼
                   电源 / NAND
```

要标出：

```text
- 每个外部实体
- 每条连接的协议和方向
- 哪些是可信的，哪些不是
```

### 这一步的价值

它逼你回答：

```text
“谁需要访问？”
“哪些访问是必须的？”
“哪条连接可以被关掉？”
```

> 很多安全问题在上下文图阶段就能发现：**多了一条没人用的入口。**

## 38.3 分层图：每层只管一件事

```text
┌─────────────────────────────────────────┐
│ 前端：网页 / TUI / CLI / 手机 App        │  展示与交互
├─────────────────────────────────────────┤
│ 传输适配：WS / BLE / Unix socket         │  字节搬运
├─────────────────────────────────────────┤
│ 会话与命令：owner、@ 命令、事件          │  业务语义
├─────────────────────────────────────────┤
│ 桥接：rpmsg                              │  A7 ↔ E907
├─────────────────────────────────────────┤
│ 固件：UART3 收发、环形缓冲                │  实时数据面
├─────────────────────────────────────────┤
│ 硬件：UART、PIO、CCU                     │
└─────────────────────────────────────────┘
```

### 分层的判据

```text
- 上层不直接操作下层寄存器
- 下层不知道有几个客户端
- 换传输不改业务
- 换硬件只改最底层
```

### 反例

```text
网页里直接拼 rpmsg 消息 → 换传输就全改
E907 里判断“是不是浏览器” → 它根本不该知道
daemon 里直接写 PIO 寄存器 → 绕过内核，必崩
```

> 分层不是画着好看，是**让改动有地方落**。

## 38.4 时序图：一次操作发生了什么

### 网页发一个字符

```text
浏览器          daemon           E907            目标板
  │  WS binary    │                │                │
  ├──────────────►│                │                │
  │               │  rpmsg write   │                │
  │               ├───────────────►│                │
  │               │                │  UART3 TX      │
  │               │                ├───────────────►│
  │               │                │                │
  │               │                │  UART3 RX      │
  │               │                │◄───────────────┤
  │               │  rpmsg read    │                │
  │               │◄───────────────┤                │
  │  WS binary    │                │                │
  │◄──────────────┤                │                │
```

### 一次 Wi-Fi 扫描

```text
浏览器          daemon           wpa_supplicant
  │  "@w scan"    │                    │
  ├──────────────►│                    │
  │               │  D-Bus Scan        │
  │               ├───────────────────►│
  │  @event queued│                    │
  │◄──────────────┤                    │
  │               │  (几秒)            │
  │               │  ScanDone signal   │
  │               │◄───────────────────┤
  │  @scan result │                    │
  │◄──────────────┤                    │
  │  @scan done   │                    │
  │◄──────────────┤                    │
```

要点：

```text
- 长操作先回“已受理”
- 结果用事件推
- 有明确的“结束”信号
```

> 时序图能暴露“哪里会阻塞”“哪里会丢”“哪里没有超时”。

### 断线重连

```text
客户端          daemon
  │  连接断开     │
  │──────────────►│  unregister
  │               │  owner 清零、epoch++
  │  重连         │
  ├──────────────►│  register（新 id）
  │  @c?          │
  ├──────────────►│
  │  owner=0      │
  │◄──────────────┤
```

客户端必须知道：**重连后 id 会变，owner 可能已经不是自己。**

## 38.5 关键取舍

### 取舍一：单核还是双核

| | 单核（全在 A7） | 双核（A7 + E907） |
|---|---|---|
| 实时性 | 受 Linux 调度影响 | E907 独立、确定 |
| 复杂度 | 低 | 高（rpmsg、固件） |
| 内存 | 只占 A7 | 多一份固件和缓冲 |
| 调试 | 常规 | 需要看两颗核 |
| 隔离 | 崩了一起崩 | 一颗崩另一颗还在 |

这块板选双核，因为：

```text
- UART3 要在 Linux 启动前就能工作（早期日志）
- 115200 下 Linux 的调度抖动足够造成丢字节
- 硬件本来就给了 E907
```

> 双核不是“更高级”，是**为实时性付复杂度**。

### 取舍二：轮询还是中断

```text
中断：低延迟、低 CPU 空闲占用，但并发复杂
轮询：简单、可预测，但高负载时 CPU 满
```

实际做法：

```text
E907：UART 用中断 + 环形缓冲（低延迟）
daemon：用 select/poll（多连接、低 CPU）
```

### 取舍三：Python 还是 C

```text
控制面（HTTP、命令、配置）：Python，开发快
数据面（高频字节）：C，开销小
```

这块板：

```text
linkr-bee-daemon  Python（控制 + 桥接）
linkr-ble         C（BLE 数据面）
E907 固件         C/Zephyr（UART 数据面）
```

> 判据是**频率和延迟要求**，不是语言偏好。

### 取舍四：内存换简单，还是简单换内存

```text
- 大缓冲：吸收突发，但常驻内存
- 大日志：好排查，但占空间/带宽
- 多线程：代码直观，但每线程有栈
```

这块板的选择：

```text
- 缓冲能大就大（64 KiB × 2 在 E907，256 KiB 在 daemon）
- 日志限频、限大小
- 线程数按连接数，接受上限
```

### 取舍五：功能 vs 可验证

```text
每加一个功能，要加：
- 一条需求
- 一条验收
- 一条回归用例
```

加不起，就先不加。**没有验收的功能是负债。**

## 38.6 架构决策记录（ADR）

### 为什么需要

半年后有人问：

```text
“为什么 E907 不直接用 Linux 的 UART 驱动？”
“为什么令牌是第一帧，不是 HTTP 头？”
“为什么 BLE 不复用 WebSocket？”
```

没有记录，就只能猜，然后可能“优化”掉关键设计。

### 格式

```markdown
# ADR-0003: UART3 由 E907 独占

## Status
Accepted (2026-11-10)

## Context
UART3 需要在 Linux 启动前输出早期日志；115200 下 Linux 调度抖动
会造成丢字节。

## Decision
UART3 由 E907 固件独占，A7 通过 rpmsg 转发。

## Consequences
+ 实时性可控
+ 早期日志可用
- 需要维护 rpmsg 协议
- 调试要跨两颗核
- A7 侧不能直接用 /dev/ttyS3
```

### 什么该记

```text
- 影响多个模块的决定
- 有争议、有替代方案的决定
- 以后可能被“优化”掉的决定
- 有外部约束的决定（EULA、硬件）
```

> ADR 不是文档负担，是**给未来的自己留的辩护词**。

## 38.7 需求没想清楚的症状

### 十个信号

```text
1. 讨论一直在“怎么做”，没人说“做到什么算完”
2. 同一个词，两个人理解不同（“实时”“稳定”）
3. 需求里全是“支持”“友好”“流畅”
4. 没有验收标准
5. 范围一直在扩大（“顺便再加一个……”）
6. 没有“不做”的清单
7. 依赖一个还没验证的假设
8. 估算按“最理想情况”
9. 没有失败路径（断网、掉电、满了）
10. 没有优先级，所有事都“必须”
```

### 怎么破

```text
- 把每条需求写成“给定…当…则…”
- 给每条需求一个数字
- 明确写“本期不做”
- 先做最小垂直切片（一条链路打通）
```

### 垂直切片

不要“先做完所有底层，再做上层”。而是：

```text
第一个切片：
浏览器输入一个字符 → E907 → UART3 → 目标板收到

哪怕只支持一个客户端、没有 TLS、没有 BLE。
```

打通一条，再横向扩展。

> 能跑的最小系统，比“设计完美但没跑过”的架构值钱一百倍。

## 38.9 常见错误清单

| 现象 | 可能原因 | 怎么查 |
|---|---|---|
| 做着做着范围爆炸 | 没有“不做”清单 | 回到需求 |
| 验收时吵起来 | 没有验收标准 | 补“怎么测” |
| 架构图没人看 | 画完不更新 | 改代码时同步 |
| 决定被推翻 | 没有 ADR | 补记录 |
| 性能不达标 | 需求没数字 | 量化 |
| 换传输要大改 | 分层破了 | 找 `if transport` |
| 一直集成不了 | 没做垂直切片 | 先打通一条 |
| 估算总超 | 忽略失败路径 | 加异常场景 |
